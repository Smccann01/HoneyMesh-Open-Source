# Network Decode Firewall Console

The original console source is licensed under Apache-2.0; see [LICENSE](LICENSE) and [license scope](LICENSE_SCOPE.md). Release artifacts and customer deployment remain subject to the support and safety gates below.

A local operator console built with the published `@network-decode/node-guard@0.2.0-alpha.11`. The application has dedicated Overview, Connections, Enforcement, Activity, Interfaces, Lab tools, and Settings screens. It shows authenticated Linux socket/interface telemetry and pinned HoneyMesh agent mode/health. A local administrator account can retain an encrypted HoneyMesh operator token for protected grant, XDP counter, and interface reads. Connection details open in a side drawer with grant lookup and a bounded source-block request. Direct write controls are a development candidate and are disabled by default. Synthetic Node Guard exercises live under Lab tools. This console does not install network rules or attach XDP.

The Firewall Console source is free. A public installable release still needs a version-matched console and agent package with installation and recovery checks. Node Guard is a standalone free application SDK. The local console account controls operator access and is not a software license.

Customer packaging uses `HM_CONSOLE_STATE_DIR=/var/lib/network-decode-firewall` so root-owned program files can remain read-only while the dedicated `networkdecode` service account owns its private credentials. The package's `packaging/CUSTOMER_INSTALL.md` describes the first-install path. This beta candidate keeps host writes disabled until the signed agent contract and recovery path are qualified together.

## Start

```sh
npm ci
npm start
```

Open `http://127.0.0.1:8787`. For first setup, obtain the one-time bootstrap token from the project folder in **your own terminal**:

```sh
node -p 'require("./.local/credentials.json").adminToken'
```

Paste it into **Create admin account** and choose a unique password of at least 16 characters. The bootstrap token can no longer sign in or access the API after setup. Sign in with the new password on other local browsers. The browser uses an HttpOnly, SameSite=Strict cookie scoped to `/api`, which survives reloads and service restarts. It expires after 30 days of inactivity and renews while the page remains active; sign in again with your password if it expires. **Sign out and revoke sessions** invalidates every browser session. Change the password in the account panel to revoke prior sessions while retaining the saved HoneyMesh token. The account is local to this installation and is **not** a HoneyMesh customer license, subscription token, or Node Pro entitlement.

The account file is `.local/operator-account.json` with owner-only permissions. The password is verified with scrypt; the HoneyMesh token is encrypted with a key derived from that password and is never sent back to the browser. Enter the current HoneyMesh **agent operator token** once in **Settings → HoneyMesh operator access**. It is different from the one-time console bootstrap token and the local account password. On the HoneyMesh host, an operator can read the current agent token with `sudo jq -r '.admin_token' /var/lib/honeymesh/runtime-state.json` and paste it into the local console; do not send it through chat or support. The root configuration may have an empty admin token because the running agent saves the generated token in its private runtime state. The console verifies it through the certificate-pinned loopback agent before saving it. On later visits, sign in with the account password; the token need not be pasted again. If the HoneyMesh token is rotated or revoked, replace it in Settings. **Do not put the token or the account file in Git, a support ticket, or a public website.** If the account password is lost, stop the service, remove `.local/operator-account.json` locally, restart, and create a new account with the local bootstrap token. This discards the encrypted HoneyMesh token; obtain a replacement from HoneyMesh SOC. Do not delete the account file while the server is running.

The connection table reads `/proc/net/tcp*` and `/proc/net/udp*`; interface totals read `/proc/net/dev`. Data is a bounded snapshot from the current process's network namespace, which may be a container rather than the whole host. Server-side filters, sorting, and 100-row pages work on the full parsed snapshot. The table and detail drawer also show the kernel socket UID, inode, and receive/transmit queue bytes when available. UID is the socket owner ID, not a verified process name. Queue bytes are buffered data at the sample instant, not per-connection throughput.

The connection drawer's **Explain host decision** control calls `GET /api/host/decision?ip=<exact-address>` through the authenticated local console and pinned agent connection. It joins the agent's UEE ownership snapshot with its enforcement contract and global XDP exact-ban counters. The result separates an agent-reported applied kernel block, an active release override, a grant awaiting reconciliation, and no active UEE grant. It names each current owner, reason, policy version, and expiry when available. The counters are **global**, not counts for that address; a socket row does not establish inbound direction or hostile intent. If the agent contract or counters are unavailable, the API says so while retaining the UEE result. The endpoint is read-only and requires the same local admin and saved agent access as other host controls.

With a new agent implementing `/api/enforcement/decision`, the console reads that exact-IP view directly and still labels global XDP counters separately. Older signed agents continue to use the existing authenticated grants snapshot for this one view. **UEE history** in the connection drawer reads up to 25 persisted reconciliation actions for the selected IP; **Preview exact-source scope** in Enforcement asks the agent whether a proposed 30-second to 24-hour operator grant is currently eligible and what it would cover. These two controls require the new agent and report an upgrade requirement on older versions. Preview is read-only even when console host writes are disabled. It is not packet replay, and it does not authorize a later block automatically.

The Overview graphs retain at most 120 samples in server memory, taken every five seconds (up to ten minutes). The established-socket graph shows observed socket counts; the RX/TX graph derives interface byte rates from successive cumulative counters. Select an interface to change the traffic graph. The graph history resets on service restart, is scoped to the process network namespace, and stores no socket endpoint addresses. A missing sample, counter reset, or truncated `/proc` read is not evidence of zero traffic. Interface totals and sample rates are shown separately from HoneyMesh XDP drops. The data includes socket endpoints and cumulative counters, not packet payloads, process identities, verified direction, per-socket throughput, or attack attribution. A row's remote endpoint may be an outbound destination; it is never treated as an attacker automatically. The row controls require a fresh snapshot and explicit confirmation before any host-wide ingress source-block request. The endpoint requires the local admin session.

The console shows public **read-only** mode and health from an installed HoneyMesh Core dashboard when `.local/agent-public.json` contains its loopback HTTPS URL and SHA-256 TLS certificate fingerprint. The current local development installation is pinned to `https://127.0.0.1:8443`. If the agent's certificate rotates, update the pin after independently checking the replacement certificate. Connection failure is shown as disconnected. **Open HoneyMesh host controls** opens the existing agent SOC dashboard in a separate tab.

For protected host reads, the server decrypts the saved operator token only after an account sign-in and checks the pinned agent certificate before forwarding it. The operator should use HoneyMesh SOC to obtain or rotate that credential; do not paste it into a public site. This console's in-memory action log is supplemental; it is lost when the process restarts.

Host writes require an explicit `HM_HOST_ACTIONS_ENABLED=1` launch setting, an active local account session, a saved operator token, same-origin requests, and a signed agent implementing enforcement contract version 1. The candidate writes are exact IPv4/IPv6 operator grants for 30–300 seconds, release of **that operator grant ID only**, and return to TEST. The agent remains the XDP authority. The older installed Core binary has no contract version 1, so source-block and scoped-release controls stay closed even if the launch flag is set. The exact new Core candidate passed scoped disposable-VM packet, natural-expiry, overlapping-grant, and reboot proofs (see `FIREWALL_CONNECTION_CONTROLS_VM_PASS_2026-11-04.md` and `FIREWALL_CONNECTION_CONTROLS_REBOOT_PASS_2026-11-04.md` in HoneyMesh-Validation). The Node Pro contract is now a source-level candidate and has not passed those VM tests. In the Node Pro candidate, a current paid host entitlement is required to create a new operator grant; exact scoped release and return to TEST remain available if the entitlement expires. VM kernel/database failure injection and all four live producers remain outside those proofs. The existing broad `/api/ban/release` remains excluded. Session termination and per-port rules require separate agent/kernel APIs.

The Enforcement form's button remains clickable when scoped writes are unavailable. It then checks account access, operator-token status, console write setting, agent contract, and host mode, and explains the blockers without sending a ban request. When the pinned agent is reachable, **Open HoneyMesh SOC** opens its local HTTPS URL in the current tab. Older installed Ed25519 leaf certificates produce `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` in the tested Chrome build. The agent packages now generate ECDSA P-256 local certificates; existing hosts need the leaf-only rotation utility and an updated console pin. After rotation, a browser may still show a private-CA warning until that CA is trusted. The console button changes to **Apply temporary block** only when its scoped-grant path is actually available. The candidate supports bounded blocks from 30 seconds through 24 hours. Permanent blocks require a separately designed persistent-policy model; the current UEE rejects grants longer than 24 hours.

Connections hover shows readable `/proc` process name and PID matches, Linux UID, queue sizes, and common remote-port labels. Process matches can be unavailable because of permissions or process churn. An explicit PTR lookup in the drawer may show a reverse-DNS name, but that name is unverified and does not establish which website was visited. Socket metadata does not contain HTTP Host or TLS SNI.

The default Node Guard policy is OBSERVE. In **Lab tools**, record two synthetic failed-login fixtures, check the restriction, compare policies, and run Security Replay. To try process-local ENFORCE behavior, restart with `npm run start:enforce`. These fixtures are not proof of an actual network client's address.

To send a signed synthetic observation from another terminal:

```sh
npm run send:webhook -- 8.8.8.8
```

The receiver verifies its body, timestamp, event ID, and HMAC. Sender authentication does not establish that the stated IP was the real sender.

## HoneyMesh integration

The public Node Guard SDK can run on its own. Real, trusted application observations can be sent over a protected Unix socket to a separately installed HoneyMesh Node agent. That agent verifies application ID, Linux peer UID, signature, source policy, and TTL before its Unified Enforcement Engine may write XDP maps. The separate operator-token entry in this local console is for administrative access to HoneyMesh Core; application observations never receive that token. No privileged enforcement code belongs in browser JavaScript.

This lab has no Node agent bridge configured. See [XDP_INTEGRATION.md](XDP_INTEGRATION.md) for the exact integration and test gate.

## Validation

`npm test` checks application policy decisions, webhook replay rejection, HTTP authorization, account persistence, password rotation, session revocation, and the candidate host-control boundary. The service binds to `127.0.0.1`, checks the Host and Origin headers, rate limits password sign-in, and sends a strict Content Security Policy. Local credentials stay in `.local` with owner-only permissions. Local OS access or a stolen authenticated browser session can still control this console. Do not expose port 8787 through a reverse proxy or public tunnel. Scoped VM packet, TTL, release, rollback, and reboot recovery proofs passed; VM injected-failure recovery remains open.
